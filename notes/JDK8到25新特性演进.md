## 一、为什么按版本分平台

每个 `jdkN-platform` 都搭了对应 JDK 的真实运行环境（不同 `maven.compiler.release` / 对应依赖），
新特性不是抄文档，而是在对应 JDK 上**跑通例子再记**。base 层覆盖该版本语言/API 新特性，tech 层覆盖对应生态。

## 二、版本覆盖清单

| 版本 | 平台 | base 覆盖的新特性（场景） |
|------|------|--------------------------|
| JDK 11 | `jdk11-platform` | `var` 局部变量推断、HTTP Client（替代 HttpClient）、`String`/`Optional` 新方法、单文件源码直接运行 |
| JDK 17 | `jdk17-platform` | **密封类 `sealed`**、`switch` 模式匹配（预览→正式）、`record`、`NullPointerException` 精确提示、`Stream`/`Optional` 增强 |
| JDK 21 | `jdk21-platform` | **虚拟线程（Project Loom）**、`SequencedCollection`、`switch` 模式匹配正式、未命名变量/模式、`String` 模板（预览） |
| JDK 25 | `jdk25-platform` | 最新演进特性尝鲜（按 GA 内容持续补充） |

## 三、最值得深入展开的两个点

### 1. 虚拟线程（JDK 21）
- 场景：`jdk21-base` 用虚拟线程跑高并发 IO 任务，对比平台线程的吞吐与内存占用。
- 关键点：**「写的同步代码，享受异步的吞吐」**；但 `synchronized` 会 pinned 虚拟线程，是落地最大坑。
- 取舍：CPU 密集型别用；IO 密集型、大量并发连接场景收益最大。

### 2. 密封类 + 模式匹配（JDK 17）
- 场景：用 `sealed interface` 限定实现类，配合 `switch` 模式匹配做**穷尽性**处理，编译器帮你兜底。
- 取舍：比「父类 + 一堆 `instanceof`」更安全、更可读，适合领域建模（如状态机、代数数据类型）。

## 四、演进脉络一句话总结
**语法更表达力（record/sealed/模式匹配）+ 运行时更轻（虚拟线程）+ API 更现代（HTTP Client）**。
升级决策上：17 是 LTS 生产甜点线，21 的虚拟线程是性能分水岭，25 持续填预览特性。
