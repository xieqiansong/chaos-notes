# 多级缓存学习记录

工程依托：[jdk21-multilevel-cache-demo](https://github.com/xieqiansong/chaos-java/tree/main/jdk21-platform/jdk21-tech/jdk21-multilevel-cache-demo)（`chaos-java` 仓库，JDK21 + Spring Boot 3.5.14，多级缓存技术 Demo：L1=Caffeine 本地 + L2=Redis Hash + 业务域 VERSION 版本号一致性，读路径靠版本号比对跳过网络 IO）。

## 1. 安装

```bash
mvn -pl jdk21-tech/jdk21-multilevel-cache-demo -am test                  # 单元测试（无需 Redis）
mvn -pl jdk21-tech/jdk21-multilevel-cache-demo spring-boot:run          # 默认内存版 L2，开箱即跑

# 接真实 Redis：激活 local profile（application-local.yml 已设 redis-enabled: true）
mvn --% -pl jdk21-tech/jdk21-multilevel-cache-demo spring-boot:run -Dspring.profiles.active=local
```

`multilevel-cache.redis-enabled=false` 时 L2 退化为内存实现（`InMemoryBackend`），无需本地 Redis 即可验证全部核心逻辑。

## 2. 两级结构

- **L1 Caffeine**：进程内本地缓存，`maximumSize` + `expireAfterWrite` TTL，避免朴素 `ConcurrentHashMap` 无界增长 OOM。
- **L2 Redis Hash**：`DEMO:{bizKey}:{key}` 存字段级 Hash；`DEMO:{bizKey}:VERSION` 存整个业务域版本号。

## 3. 版本号一致性

- 任一节点 `put` 时 L2 版本号自增（`INCR`）。
- 读路径先查 L1；L1 命中后**比对本地记录的版本号与 L2 当前版本号**：
  - 一致 → 直接返回本地副本，**跳过网络 IO 与反序列化**（高频读场景收益最大，120ms→20ms 量级）。
  - 不一致 → 回源 L2 刷新 L1。
- 删除/更新 → 版本号自增 → 其他节点 L1 自然失效，无需广播。

## 4. 并发安全

用 `ReadWriteLock` 保护「L1 读取 + 版本号判断 + L1 写入」临界区，避免竞态下 L1 命中但版本号未刷新的脏读。

## 5. 读写失效链路

- **读 get**：L1 命中且版本号一致 → 零网络 IO 返回；否则回源 L2 → 刷新 L1；L2 未命中 → `loadFromSource`（当前为内存 `ConcurrentHashMap` 模拟，未接数据库）。
- **写 put**：先 L2（写 Redis Hash + VERSION 自增）后 L1，保证其他节点靠 VERSION 感知变更。
- **失效 remove**：删 L2 Hash + VERSION 自增 → 其他节点 L1 下次读判为「不一致」；本节点清 Caffeine + localVersionMap。

## 踩坑

- **顺序：先 L2(带版本号) 后 L1**：否则其他节点无法靠 VERSION 感知变更。
- **版本号比对是免广播一致性的关键**：写只 INCR 版本号，读侧自行判断失效，避免 Redis Pub/Sub 广播的复杂度与丢消息风险。
- **临界区要加锁**：L1 命中与版本号判断之间若无锁，可能脏读旧值。
- **L1 必须限大小**：用 Caffeine 而非裸 Map，否则 OOM。
- **当前未接数据库**：`loadFromSource` 是内存模拟，真实场景替换为 JdbcTemplate/MyBatis/JPA。

## 进阶方向

- 与 `jdk8-localcache-demo` 的「缓存穿透/击穿/雪崩」防护结合（空值缓存/布隆过滤器、互斥锁、随机 TTL 抖动）。
- 版本号基于真实数据变更事件（binlog/消息）驱动，而非仅 put 时自增。
- 监控：Caffeine `stats()` + Redis 命中率接入 Prometheus。
