# 短链系统设计（场景总结 + 要点）

> 工程来源：[chaos-java/jdk8-short-link-demo](https://github.com/your-username/chaos/blob/main/chaos-java/jdk8-platform/jdk8-short-link-demo)
> 分类：场景类 · 总结场景 + 要点

## 一、这个场景要解决什么

短链服务的本质是「长 URL ↔ 短 code」的映射 + 高并发跳转。这是系统设计中的经典考题：
**如何发号（不重复、可扩展）、如何挡住缓存穿透、跳转如何快**。

核心诉求：
1. 短码全局唯一、尽量短（节省字符、好看）；
2. 跳转读多写少，读链路必须极快；
3. 大量「不存在的短码」请求不能打到数据库（缓存穿透）。

## 二、链路总览

```
写：长URL ─▶ Snowflake发号 ─▶ Base62编码 ─▶ 存 Redis+PG ─▶ 返回短码
读：短码  ─▶ 布隆过滤器(存在?) ─否─▶ 直接404(防穿透)
                    │是
                    ▼
               Redis 取长URL ─否─▶ PG 回源 ─▶ 写回Redis
                    │
                    ▼
               302 跳转
```

## 三、关键设计（带代码落点）

### 1. 发号器：Snowflake + Base62
Snowflake 生成 64 位趋势递增 ID，再用 Base62 编码成短字符串，比十六进制更省字符。

```java
// SnowflakeIdGenerator：41bit 时间戳 + 10bit 工作节点 + 12bit 序列号
// Base62Util 把 long 编成 [0-9a-zA-Z]，8 位就能表示约 2.18e14 个值
String code = Base62Util.encode(snowflake.nextId());
```
> 说明：Snowflake 的「时钟回拨」是经典坑，生产要加 clock 偏移缓存 / 等待策略。
> 想要更短还能用「号段模式（Leaf-segment）」预分配，本项目 jdk8-base 也有 Leaf 实现可对照。

### 2. 防缓存穿透：Redis 布隆过滤器
所有「合法存在的短码」进布隆过滤器；查询先过布隆，不存在直接 404，绝不落库。

```java
// BloomFilterConfig：千万级元素、1% 误判率
RBloomFilter<String> bf = redissonClient.getBloomFilter("short-key-bloom");
bf.tryInit(10_000_000L, 0.01);
```
> 说明：布隆过滤器挡的是「一定不存在」，误判的那 1% 会放过（宁可放过不可误杀），
> 所以 PG 回源那一层仍然是最后防线。它和「缓存空值」是两种思路：布隆省内存、空值简单。

### 3. 跳转：302 + 多级缓存
Redis 命中直接返回长 URL 做 302；未命中回源 PG 并回填 Redis，TTL 控制。

## 四、要点（技术总结）

1. **读链路要短、写链路可以重**：短链 99% 是读，优化重点永远在跳转这条线。
2. **布隆过滤器不是银弹**：它是「概率型」结构，要配合真实存储做最终兜底；
   误判率、元素规模要按业务预估，初始化后不可改（Redisson 重建需重新灌数据）。
3. **发号策略决定短码长度与冲突率**：Snowflake 趋势递增可能泄露发号量，
   若在意可加随机盐 / 非连续编码，代价是更长的码或额外查重。
4. **Base62 比 Base64 更适合 URL**：去掉了 `+ / =` 这些需要 URL 编码的字符。

## 五、还能怎么演进
- 高基数下分片布隆过滤器；
- 短码加盐防遍历；
- 跳转增加 A/B、访问统计等增值能力（读链路天然适合做埋点）。
