# 接口幂等学习记录

工程依托：[jdk21-idempotent-demo](https://github.com/xieqiansong/chaos-java/tree/main/jdk21-platform/jdk21-tech/jdk21-idempotent-demo)（`chaos-java` 仓库，JDK21 + Spring Boot 3.5.14，用三层去重（请求级幂等号 / 消费级 messageId / 状态机级终态）统一演示「重复发生也不重复副作用」，H2 内存去重表开箱即跑）。

## 1. 安装

```bash
mvn -pl jdk21-tech/jdk21-idempotent -am test        # 断言全部核心语义
mvn -pl jdk21-tech/jdk21-idempotent spring-boot:run  # 控制台主线演示
```

> 接口幂等不是「防止重复请求发生」，而是**在 at-least-once 投递语义下，重复发生了也不造成重复副作用**。

## 2. 三层去重

| 场景 | 去重键 | 类 | 说明 |
|---|---|---|---|
| 请求级并发双发 | requestId | `ConcurrentDoubleSubmitDemo` | 前端/网关超时重发，唯一约束保证仅一次副作用 |
| 消费级重复投递 | messageId | `ConsumeDedupDemo` | MQ at-least-once 重发，消费侧去重 |
| 状态机级重复回调 | bizNo(终态) | `StateMachineDedupDemo` | 上游重试回调，已终态忽略 |

## 3. 调用链路（共用）

三层防护共用同一条核心调用链，差异仅在「去重键来源」与「重复后的处理动作」：

```
调用方
  └─> Guard（RequestIdempotentGuard / ConsumeIdempotentGuard / StateMachineGuard）
        └─> IdempotencyStore.tryMarkFirst(record)       // 原子首检
              └─> H2IdempotencyStore（唯一约束 k+scope）
                    ├─ INSERT 行数 == 1  → 首检通过：执行真实业务副作用
                    └─ DuplicateKeyException → 首检失败：直接返回占位 / 跳过，绝不重复副作用
```

首检原子性由数据库唯一约束保证，并发双发（两个相同 requestId 同时到达）下仍只放行一个事务。

## 4. 场景详解

- **请求级（并发双发兜底）**：`tryMarkFirst` 用 `INSERT ... (k, scope) UNIQUE` 的受影响行数判定首检；冲突抛 `DuplicateKeyException` → 返回 `false`。`@Transactional` 把「首检 INSERT」与「业务写」包在同一事务，消除「首检成功但业务回滚、重复请求又进来」的窗口。
- **消费级**：去重键来自 broker（messageId）；重复投递直接 `return` 跳过，保证同事件只处理一次（避免重复扣款/通知）。
- **状态机级**：以「业务单号 + 终态」为去重键；单子到达终态后，后续同单号回调直接忽略。靠业务状态本身不可重复迁移天然去重，并叠加去重表双保险。

## 踩坑

- **单线程「SELECT 再 INSERT」有竞态**：两相同请求同时穿过 SELECT 都判首检成功，副作用执行两次。**唯一约束 + 受影响行数**把首检变成数据库原子操作，并发双发下仍只放行一个。
- **事务边界必须包住首检与业务写**：否则「首检成功但业务回滚、重复请求又进来」形成窗口。
- **去重表自身成瓶颈**：无限增长需 TTL 清理/归档/冷热分离。
- **跨服务去重**：多实例下用 Redis `SETNX` 或 DB 唯一约束做分布式首检；分布式锁（Redisson）可作补充。
- **幂等 + 对账互补**：幂等防「重复写」，对账防「漏写」——两者一起构成分布式写安全。

## 进阶方向

- 存储与过期：TTL 清理/归档/冷热分离。
- 跨库/跨服务：Redis `SETNX` / DB 唯一约束 / Redisson 分布式锁。
- 与最终一致性对账衔接；请求级（粗粒度去重表）+ 状态机级（细粒度）分层防护。
