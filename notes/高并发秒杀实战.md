# 高并发秒杀实战（场景总结 + 要点）

> 工程来源：[chaos-java/jdk8-seckill-demo](https://github.com/your-username/chaos/blob/main/chaos-java/jdk8-platform/jdk8-seckill-demo)
> 分类：场景类 · 总结场景 + 要点

## 一、这个场景要解决什么

秒杀是典型的「瞬时海量请求 + 极少量库存」场景，核心矛盾只有一句话：
**如何在数据库撑不住的写入压力下，保证不超卖、且系统不被打垮**。

拆开看要做四件事：

| 难题 | 朴素做法的坑 | 本项目的做法 |
|------|------|------|
| 超卖 | `select` 后 `update` 非原子，并发下多扣 | Redis Lua 分桶库存原子扣减 |
| 数据库被打爆 | 每个请求都落库 | Kafka 异步削峰，下游慢慢消费 |
| 流量过猛 | 恶意刷接口 / 突发洪峰 | 令牌桶限流（本地 + Redis 双层） |
| 库存查不到就穿透 | 请求直冲数据库 | 库存预加载 + 布隆过滤器兜底 |

## 二、链路总览

```
            ┌─────────────┐
请求 ──────▶│ 令牌桶限流   │ (本地 Guava + Redis 双层，挡掉突发洪峰)
            └──────┬──────┘
                   ▼
            ┌─────────────┐
            │ 库存校验 Lua │ (Redis 分桶库存，原子扣减，防超卖)
            └──────┬──────┘
                   ▼ (扣减成功才放行)
            ┌─────────────┐
            │ 下单消息     │ ──▶ Kafka ──▶ 消费者异步落库 (削峰)
            └─────────────┘
```

## 三、关键设计（带代码落点）

### 1. 防超卖：Redis Lua 分桶库存
库存不放在一个 key 里，而是拆成多个「桶」，扣减时按路由取一个桶做原子扣减，
既降低单 key 竞争，又保证整段库存总量守恒。

```lua
-- stock_bucket.lua（核心：单桶内原子扣减，返回是否成功）
local bucket = KEYS[1]
local req = tonumber(ARGV[1])
local cur = tonumber(redis.call('GET', bucket) or '0')
if cur >= req then
  redis.call('DECRBY', bucket, req)
  return 1
end
return 0
```
> 说明：扣减逻辑必须放在 Lua 里一次性执行，否则「读-改-写」在 Redis 多命令间会有竞态。
> 分桶还能把热点打散到多个 key，避免单 key 成为瓶颈。

### 2. 令牌桶限流（参考已沉淀的[多租户限流笔记](../performance/多租户分布式限流-本地加Redis双层限流.md)）
本地令牌桶挡住进程内突发，Redis 令牌桶做集群级总量控制，两层叠加。

### 3. 异步削峰：Kafka
秒杀成功 = 「扣减 Redis 库存 + 发一条下单消息」。真正创建订单、扣账户是消费者异步做的。
前端拿到「排队中」即可，不用同步等 DB 写完。

## 四、要点（技术总结）

1. **先挡后扣再异步**：限流（挡）→ 库存（扣，必须原子）→ MQ（异步）。顺序不能乱，每一层都在替下一层减负。
2. **能用 Redis 原子操作就别上锁**：分布式锁（Redisson）也能防超卖，但 Lua 更轻、无锁等待，QPS 上限更高。锁是兜底，不是主路径。
3. **库存要预热**：开抢前把 DB 库存 load 进 Redis，否则第一波请求全打到库上。
4. **异步带来一致性的妥协**：极端情况下 Kafka 消费失败要补偿/对账，这是「最终一致」而非「强一致」，要和业务方对齐预期。
5. **压测优先于优化**：见[秒杀链路压测与优化](../performance/秒杀链路压测与优化.md)，先有数据再谈调优。
