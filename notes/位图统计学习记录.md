# 位图统计学习记录

工程依托：[jdk8-bitmap-stat-demo](https://github.com/xieqiansong/chaos-java/tree/main/jdk8-platform/jdk8-tech/jdk8-bitmap-stat-demo)（`chaos-java` 仓库，纯 JDK8 零依赖，承接 1200 万设备接入场景，演示 Bitmap 压缩存储 + O(1) 聚合、大 key 拆分优化，并以 HyperLogLog 作 UV 的「精确 vs 近似」对比）。

## 1. 安装

```bash
mvn -pl jdk8-tech/jdk8-bitmap-stat-demo test        # 位操作/BITOP/分片/HLL 单测
java -cp jdk8-tech/jdk8-bitmap-stat-demo/target/classes lan.chaos.bitmap.BitmapStatDemo   # 六场景演示
```

## 2. 核心痛点与容量账（1200 万设备）

| 方案 | 单设备 | 1200 万占用 | 说明 |
|---|---|---|---|
| Bitmap（1 bit/设备） | 1 bit | ≈1.43 MB | 连续内存、cache 友好 |
| byte[]（1 B/设备） | 1 B | ≈11.4 MB | 小整型状态 |
| Set<String>（估算） | ≈104 B | ≈1.19 GB | String + HashMap.Node 开销 |
| HyperLogLog（16384 寄存器） | 恒定 | ≈12 KB | 与基数无关，代价 ~0.81% 误差 |

Bitmap 把「在线/日活状态」压到 ~1.43 MB，统计用 `BITCOUNT`（`Long.bitCount`，CPU 位运算，cache 友好）。

## 3. 六个场景

- **A 在线状态**：`SETBIT` 上下线、`GETBIT` 查询、`BITCOUNT` 实时在线数。
- **B 日活统计**：按天一个位图，`BITOP OR` 近 N 天活跃、`AND` 连续活跃（按天分 key = 时间维度分片）。
- **C 内存账对比**：Bitmap vs byte[] vs Set 量级差异。
- **D 吞吐对比**：GETBIT vs Set.contains；BITCOUNT vs Set.size（cache 友好性）。
- **E 大 key 拆分优化**（见下）。
- **F UV 统计对比**：Bitmap 精确 UV vs HyperLogLog 近似（600 万访问 → 300 万 UV，误差 ~0.81% vs 恒定 12 KB）。

## 4. 大 key 位运算瓶颈与拆分（场景 E）

两层瓶颈：算法层 `BITOP` 是 O(N)、`BITCOUNT` 全量扫描 O(N/64)；执行层 Redis 单线程，一次大 key 位运算占住主循环，**后续所有命令整体排队**——危害是「整条链路尾延迟被拉长」。

| 方案 | 机制 | 取舍 |
|---|---|---|
| 哈希分片 | `crc32(deviceId) % N` | 数据均匀无热点；全局统计需跨片聚合 |
| 区域分片 | 设备 ID 前缀（地市码） | 统计即分区，单区域零聚合；区域间可能不均 |
| 增量计数 | `SETBIT 0→1` 时 count++、`1→0` 时 count-- | 在线数/日活 O(1) 直读，绕开 BITCOUNT；代价是多一次计数维护 |
| 时间分片 | 按天分 key | 天然滚动统计（场景 B） |

## 5. HyperLogLog 近似统计（场景 F）

- 哈希：MurmurHash3 x64（分布均匀是估算准确前提）。
- 寄存器定位：低 p 位 → 下标；其余位从最高位起数连续 0 + 1 作为 rank，保留历史最大。
- 估算：调和平均 `E = α·m² / Σ 2^(-reg)`；小基数（`E ≤ 2.5m` 且有空寄存器）用 LinearCounting 修正，否则系统性低估。
- 与 Redis 语义对照：`PFADD`≈`pfadd`、`PFCOUNT`≈`pfcount`（Redis 还支持 `PFMERGE` 按天合并周/月 UV，本 demo 未实现）。

## 踩坑

- **Bitmap 精确有代价**：内存随基数上界线性增长，且必须先知道设备总量才能分配位图；UV 这类只关心量级的指标换 HLL 更划算。
- **大 key 是尾延迟杀手**：单线程位运算阻塞整条链路，必须分片或增量计数。
- **HLL 误差与数据规模无关**：hash 质量决定上限，小基数需 LinearCounting 修正，6-bit 打包省内存。
- **底层换算**：`words[offset>>>6]` 定位 long、`1L << (offset & 63)` 定位位（64 位宽位运算吞吐高于 byte 粒度）。
