## 一、这个场景要解决什么

不是「能不能跑一个服务」，而是「一个能上线级别的多服务协作骨架」该长什么样。
我以 Spring Cloud Alibaba 为载体，按 **P0→P6** 路线图逐步落地，每个阶段都接真实中间件（绝不写模拟桩）。

## 二、阶段成果（进度总览）

| 阶段 | 主题 | 关键交付 |
|------|------|----------|
| P0 | 骨架 | 父 BOM + docker-compose（Nacos/PG/MySQL/Redis）+ 多模块空壳 |
| P1 | 公共基础 + 数据层 | `R<T>` 统一响应、全局异常、`traceId`、多数据源（PG 主 / MySQL 副）、user CRUD |
| P2 | 熔断限流 | 网关 Sentinel 流控 + Feign 熔断降级兜底 |
| P3 | 分布式事务 | Seata AT 模式，order+account 跨库回滚，两种数据源接入姿势都演示 |
| P4 | 安全认证 | 双令牌 JWT（access 30min / refresh 7d 可吊销）+ 网关集中鉴权 + 方法级 `@RequiresPermission` |
| P5 | 可观测补全 | Feign 身份透传 + 访问日志脱敏切面 + 可选 SkyWalking 拓扑 |
| P6 | 进阶 | Nacos Config 多环境（dev/test/prod）+ `@RefreshScope` 动态刷新 + 本地默认值兜底 |

## 三、几个值得讲透的设计决策

### 1. 统一响应与异常（P1）
`common-web` 的 `ResponseAdvice` 自动把领域对象包成 `R<T>`，`GlobalExceptionHandler` 收敛所有异常。
> 说明：约定优于配置，下游不用关心包装，前端只看 `code/data/msg` 三字段。

### 2. 多数据源异构库（P1）
同应用内用 `dynamic-datasource` 的 `@DS("mysql")` 把 `UserTag` 切到 MySQL，`User` 走 PG。
> 说明：证明「一个服务可以按需路由不同存储」，比单纯读写分离更有说服力。

### 3. 分布式事务两种姿势（P3）
- `ms-order` 单库：Seata 自动代理数据源（`enable-auto-data-source-proxy`）；
- `ms-user` 多源：走 dynamic-datasource 原生 Seata 集成（关掉自动代理）。
> 说明：不同数据源结构下事务接入姿势不同，都跑通才算真懂，而不只是会加 `@GlobalTransactional`。

### 4. 双令牌 + 网关集中鉴权（P4）
accessToken 无状态 HS256 本地验签；refreshToken 存 Redis 可吊销。网关 `AuthGlobalFilter` 短路非法请求。
> 说明：鉴权放网关，下游只认透传的 `Authorization`，避免每个服务重复实现。

### 5. 脱敏访问日志（P5）
`AccessLogAspect` 打印「方法/脱敏入参/耗时/traceId」，`SensitiveMasker` 按字段名或 `@Sensitive` 注解打码。
> 说明：可观测和合规要一起做，密码/token 绝不能落盘。

### 6. 配置中心优雅降级（P6）
`spring.config.import: optional:nacos:...` + `fail-fast:false`，**断 Nacos 也能用本地默认跑起来**。
> 踩坑：Spring Cloud 2021.0.x 默认关 bootstrap 上下文，必须显式引 `spring-cloud-starter-bootstrap`；
> `spring.config.import` 在 nacos 在 classpath 时会硬校验，离线测试要关掉 nacos/config 客户端。

## 四、要点（技术总结）

1. **路线图式落地比一步到位强**：P0→P6 每步可编译可测，体现工程节奏感。
2. **真实中间件 > 模拟桩**：docker-compose 一把起齐，演示的是真链路，不是玩具。
3. **可观测是架构的刚需**：traceId 跨进程连续 + 脱敏日志，出了问题能查。
4. **降级思维贯穿始终**：配置中心断网、Redis 挂掉都有兜底，系统韧性来自这些细节。
