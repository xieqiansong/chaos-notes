# 秒杀链路压测与优化

> 工程来源：[chaos-java/jdk8-seckill-demo](https://github.com/your-username/chaos/blob/main/chaos-java/jdk8-platform/jdk8-seckill-demo)
> 分类：性能类 · 压测数据为核心
> 关联场景笔记：[高并发秒杀实战](../notes/高并发秒杀实战.md)

## 一、压测目标
对「限流 → Redis Lua 扣库存 → Kafka 异步落库」整条链路做容量摸底，回答：
**单机（单 Redis 节点）能扛多少 QPS？瓶颈在哪一环？超卖是否为零？**

## 二、瓶颈分析（压测前预判）
- 同步落库：DB 写入是最大瓶颈，必须异步化（Kafka 削峰）。
- 库存扣减：若用 DB 事务或分布式锁，单 key 竞争会锁死；改用 Redis Lua 分桶原子扣减。
- 流量整形：限流缺失时，Redis 与 Kafka 都会被突发打满。

## 三、压测方案
- 工具：JMeter / wrk，固定 1000 并发线程，阶梯加压（1000 → 5000 → 10000 QPS 目标）。
- 场景：商品库存 1000 件，请求总量 5 万（含大量超量抢购以制造竞争）。
- 观测：Redis 命中率、Kafka 消费延迟、DB 写入 TPS、超卖计数、接口 P99 耗时。
- 校验：最终「已售件数 + 售罄标记」严格等于 1000，零超卖。

## 四、实测数据（⚠️ 以下为示意框架，请以你本地实测回填）
| 方案 | 目标QPS | 实际峰值QPS | P99(ms) | 超卖 | DB峰值TPS | 备注 |
|------|---------|------------|---------|------|-----------|------|
| 朴素同步落库 | 1000 | ~320 | 1800 | 有（竞态） | 320 | 直接打库，不可行 |
| +分布式锁(Redisson) | 1000 | ~900 | 260 | 0 | 900 | 锁等待拉高延迟 |
| +Redis Lua 分桶 | 3000 | ~2800 | 45 | 0 | 2800(经MQ) | 扣减无锁，延迟骤降 |
| +Lua+Kafka异步 | 5000 | ~4600 | 38 | 0 | 受消费端限速 | 削峰，DB 不再被直冲 |
| +双层令牌桶限流 | 5000 | ~4800 | 36 | 0 | 受消费端限速 | 洪峰被挡在门外 |

## 五、结论（趋势，待实测确认）
1. **Redis Lua 分桶**相比分布式锁，扣减延迟从百毫秒级降到十毫秒级，是秒杀吞吐的分水岭。
2. **Kafka 异步**把 DB 从「同步瓶颈」变成「按消费能力匀速写入」，链路不再被 DB 拖死。
3. **双层限流**保护 Redis/Kafka 不被突发洪峰冲垮，P99 最稳。
4. 全链路**零超卖**，库存守恒由 Lua 原子性保证。
