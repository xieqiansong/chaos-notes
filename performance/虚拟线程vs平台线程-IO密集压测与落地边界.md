# 虚拟线程 vs 平台线程：IO 密集压测量化与落地边界

> 性能优化 · 实战案例。对应 GitHub 工程：[chaos-java/jdk21-platform/jdk21-tech/jdk21-virtualthread-demo](https://github.com/xieqiansong/chaos-java/tree/master/jdk21-platform/jdk21-tech/jdk21-virtualthread-demo)。

一个聚合查询接口，要并行查好几个统计指标（各查各的表、各调各的服务），接口里几乎全是等待——等 DB、等远程调用。原来的模型是 Tomcat 默认线程池（200 线程）+ 业务侧聚合查询，一压就排队：线程被阻塞占满，多出来的请求堆在队列里，接口 p99 先崩。

后来把 Tomcat 的执行器和聚合查询的执行器都换成了虚拟线程。但"换了之后快多少"这件事光靠感觉说不清——接口一排队，到底是线程不够还是下游慢，没有数据根本判断不了，也没法判断这个改动值不值。

所以这篇干脆把收益压出来：五个场景、同一套引擎、一条命令自动出报告，把「收益多大」和「哪些场景别换」都量化掉。

## 现状与瓶颈

- **实现**：Tomcat 默认线程池（`maxThreads` 200）承载请求；聚合查询接口并行查多个指标，用的也是平台线程池。
- **瓶颈**：阻塞型 IO 期间线程被占住不动，池子一满请求就排队。排队不体现为"处理变慢"，而体现为 p99 飙升——这点在压测里看得非常清楚（见实测一）。

## 替换方案

### 设计

- **Tomcat 请求线程**：`TomcatProtocolHandlerCustomizer` 里把 executor 换成 `Executors.newVirtualThreadPerTaskExecutor()`（Spring Boot 3.2+ 也可直接 `spring.threads.virtual.enabled=true`）。一个请求一个虚拟线程，阻塞即卸载。
- **多指标并行编排**：虚拟线程执行器 + `CompletableFuture` 并行查多个统计指标再聚合。这种场景天然契合——每个子查询都是纯等待。
- **批量并发查询**：列表页要逐条查外部服务状态时，用虚拟线程并发 + `ConcurrentHashMap` 收集结果，把 N 次串行往返压成 1 次最慢往返。
- **上下文传递**：虚拟线程也是线程，`ThreadLocal` 能继承；但池复用 / 异步切换场景下必须显式传递并在结束时清理（`RequestContextHolder` 手动 set / reset），否则上下文串台。

### 什么时候**不该**换（边界比用法更重要）

1. **CPU 密集任务**：虚拟线程买的是"等待"，不是"算力"。瓶颈在核数，换什么都不涨——实测四给了数据。
2. **需要限流 / 背压的场景**：虚拟线程近乎无限，压根起不到限流作用。批量处理这类需要背压的地方，仍然用固定线程池 + `CallerRunsPolicy`（池和队列都满就让业务线程自己跑，自然降速不 OOM）。
3. **临界区内阻塞**：`synchronized` 里做阻塞 IO 会 pin 住载体线程，虚拟线程直接退化成平台线程——实测三，67 倍差距。

## 压测方案

基准做成 **SpringBootTest 一键跑**：场景矩阵定义在五个 `BenchXxx` 场景类里，`mvn test -Dbench=true` 跑完约 15s 并自动写出 markdown 报告（工程 `TEST_REPORT.md` + `target/bench-results.md`）。

- **引擎**：`BenchEngine`，**闭环负载**——控制在途任务数，提交前取许可、完成后归还。一次性全灌测到的是队列深度，不是稳态。
- **延迟口径**：记「提交 → 完成」的端到端时间，**含排队**。只看执行耗时会把排队代价藏起来，得出"平台线程其实也挺快"的错误结论。
- **对照实现**：平台线程池 = 固定线程 + 有界队列 + AbortPolicy（贴近生产配置）；虚拟线程 = `newVirtualThreadPerTaskExecutor`（无队列上限）。
- **指标**：吞吐（成功数/墙钟耗时）、p50/p99、被拒绝的任务数。
- **环境**：Windows 11 / JDK 21.0.11 / 12 核。纯内存模拟场景（实测一到四）连跑多次差异 <3%；HTTP 场景（实测五）抖动 ±10~20%，改跑 5 轮取中位数并按区间表述。

### 实测一：IO 密集吞吐（对应并行编排类场景）

任务 4000，平台池固定 200 线程，每任务阻塞等待：

| 用例 | 模式 | 吞吐(任务/s) | p50(ms) | p99(ms) | 提升 |
|---|---|---|---|---|---|
| 并发 1000 / 等待 20ms | 平台线程池(200) | 6,547 | 153.6 | 154.8 | — |
| | 虚拟线程 | 32,787 | 29.5 | 31.4 | **5.0 倍** |
| 并发 2000 / 等待 20ms | 平台线程池(200) | 6,504 | 304.0 | 308.6 | — |
| | 虚拟线程 | 62,500 | 30.4 | 36.9 | **9.6 倍** |
| 并发 2000 / 等待 100ms | 平台线程池(200) | 1,855 | 1,075.7 | 1,079.5 | — |
| | 虚拟线程 | 18,433 | 107.2 | 109.7 | **9.9 倍** |

要点：

- **并发从 1000 涨到 2000，平台池吞吐纹丝不动（6,547 → 6,504），虚拟线程接近翻倍。** 平台池的吞吐被 `线程数 / 单任务耗时` 锁死，多加的并发只变成队列长度。这是整个压测里最硬的一条证据。
- **先崩的是尾延迟**：并发 2000 时平台池 p99 = 308ms，而单任务本身只等 20ms——15 倍差距全是排队。只看平均延迟会漏掉这段，而调用方感知到的"卡"正是这里。
- 虚拟线程 p99 31ms 略高于单任务 20ms，多出来的是调度与提交开销，属正常水位。

### 实测二：饱和 → 排队 → 拒绝（对应请求量打穿 Tomcat 线程）

任务 10000，在途并发 2000，平台池 100 线程 + 队列 500：

| 模式 | 吞吐(任务/s) | 平均延迟(ms) | p50(ms) | 成功 | 拒绝 |
|---|---|---|---|---|---|
| 平台线程池(100,队列500) | 1,626 | 213.6 | 183.1 | 600 | **9,400** |
| 虚拟线程(无队列上限) | 32,573 | 61.2 | 61.4 | 10,000 | **0** |

要点：

- **别被平均延迟骗了**：平台池 avg 213ms 看着不致命，但 94% 的请求压根没执行，是"快速失败"返回的。被拒绝的请求延迟接近 0，把平均值拉了下来。读这一组必须把「成功/拒绝」和吞吐放在一起看。
- 成功 600 = 100 线程 + 500 队列，与承载上限精确吻合。
- 换成**无界队列**不会拒绝，但 p99 会一路飙升——本质是把压力转成延迟，不是消除压力。所以生产上到底用有界还是无界，是在「拒绝用户」和「让用户等」之间做选择。

### 实测三：synchronized pinning（换虚拟线程但不换锁 = 白换）

两组**都用虚拟线程**，唯一差别是锁的类型。任务 800，临界区内阻塞 20ms，每个任务持有自己的锁（排除锁竞争）：

| 模式 | 吞吐(任务/s) | p50(ms) | p99(ms) |
|---|---|---|---|
| 虚拟线程 + synchronized(阻塞) | 385 | 1,048.0 | 2,047.9 |
| 虚拟线程 + ReentrantLock(阻塞) | 25,806 | 30.8 | 31.2 |

要点：

- **64 倍差距**。pinned 版吞吐 385/s ≈ 12 核 / 20ms，退化到"载体线程数"的并发能力，跟同规格平台线程池没什么两样。
- 最坑的地方在于：**表面上看你已经换了虚拟线程**，代码里也确实是 `newVirtualThreadPerTaskExecutor`，但路径上还挂着 `synchronized` 的同步工具类或三方库（连接池、驱动里很常见），收益直接归零。
- JDK 24 的 JEP 491 才修复。JDK 21 上要么改用 `ReentrantLock`，要么保证临界区内不做阻塞调用。定位手段：`jcmd <pid> Thread.dump`、`-Djdk.tracePinnedThreads=full`。

### 实测四：CPU 密集适用边界（不该换的场景）

纯计算任务 2ms × 3000，平台池线程数按核数配到最优（12）：

| 模式 | 吞吐(任务/s) | p99(ms) |
|---|---|---|
| 平台线程池(12=核数) | 5,837 | 508.2 |
| 虚拟线程 | 5,871 | 504.0 |

要点：

- **1.01 倍，就是噪声**。平台池已经按核数配到最优了，虚拟线程再怎么调度也突破不了核数上限。
- 结论是**不要换**，而不是"换得更差"——CPU 密集任务换虚拟线程没有收益，还要额外付调度和栈内存的开销。

### 实测五：HTTP 服务只换 executor（对应 Tomcat 替换）

JDK 内置 `HttpServer`，唯一变量是 `setExecutor()` 传进去的执行器；请求 3000，单请求内阻塞 20ms：

| 服务端配置 | 模式 | 吞吐(请求/s) | p50(ms) | p99(ms) | 提升 |
|---|---|---|---|---|---|
| 池 50 线程 / 并发 300 | 平台线程池 | 1,894 | 153.7 | 172.9 | — |
| | 虚拟线程 | 7,246 | 42.2 | 59.3 | **3.8 倍** |
| 池 200 线程 / 并发 300 | 平台线程池 | 7,916 | 33.8 | 60.6 | — |
| | 虚拟线程 | 8,333 | 31.7 | 51.3 | **1.05 倍** |

> **本场景抖动明显，倍数要看区间**：同一配置连跑 6 次，平台侧 6.1k~7.9k、虚拟侧 7.6k~11.0k（±10~20%），所以这里跑 5 轮取中位数。多次观测下来是 **池 50 → 3.8~5.4 倍，池 200 → 1.05~1.7 倍**，方向稳定，但单点数字复现不了。

要点：

- **池越大差距越小**（多次观测一致）：50 线程时 3.8~5.4 倍，加到 200 线程只剩 1.05~1.7 倍。说明"把线程池调大"确实能追一部分，代价是 200 个 OS 线程常驻（内存 + 上下文切换）。虚拟线程是用极少的载体线程拿到同等甚至更好的吞吐。
- **真实链路的提升倍数会被协议栈稀释**：同样是 20ms 阻塞，纯内存模拟（实测一）能差 5～10 倍，套上 HTTP 栈只剩 1～5 倍。评估收益要看"等待时间占整条链路的比例"——等待占比越高，虚拟线程收益越大。所以**别把压测里的倍数直接搬到线上评估**，真实系统里一定更低。
- **抖动本身也是一条结论**：虚拟线程侧波动（7.6k~11.0k）比平台侧大得多，因为它不再被线程数限流、直接吃满 CPU 和网络栈，机器一忙就掉。这反过来说明——瓶颈已经从"线程数"转移到了 CPU 和协议栈。

## 踩过的坑

1. **拒绝数被算成两倍**：`ExecutorFactory` 的 `RejectedExecutionHandler` 里 `rejected.incrementAndGet()` 后又抛异常，`BenchEngine` 捕获时再 +1，于是出现"成功 600 + 拒绝 18,800 > 总任务数 10,000"的荒唐结果。改成工厂只抛异常、引擎统一计数，修复后核算闭合（600 + 9,400 = 10,000）。**计数分散在多处，是压测工具最常见的自伤。**
2. **HTTP 场景偶发 17 例建连失败**：`HttpServer.create(addr, 0)` 的 backlog 用系统默认值，并发建连阶段偶发连接被拒，被误记成业务失败。显式给 backlog = 1024 后归零。
3. **压测拖慢日常测试**：完整矩阵 13s+ 且数据受机器负载影响，不适合进 CI 门禁。用 `@EnabledIfSystemProperty(named = "bench", matches = "true")` 默认跳过，另拆 `BenchSanityTest` 用极小参数守住"引擎算得对"这条底线——引擎要是算错了吞吐，报告里所有数字都是废的。
4. **客户端先成瓶颈**：HTTP 压测的客户端一开始用默认线程池，300 并发就把客户端自己压满了，测出来的差异全是客户端的。客户端也换成虚拟线程执行器后才测到服务端真实能力。
5. **HTTP 场景单次采样不可信**：连跑 6 次，虚拟线程侧吞吐在 7.6k~11.0k 之间跳（±10~20%），第一次跑出来的"5.3 倍"第二天就复现不了。改成跑 5 轮取中位数，报告里按区间写。这一点值得单独记一笔：**倍数好看不等于结论可信**，能复现的区间比一个漂亮的单点数字有用得多。
6. **`HttpClient` 的 executor 泄漏**：`.executor(Executors.newVirtualThreadPerTaskExecutor())` 把执行器直接 new 进 builder、不留引用，之后就再也关不掉了，连跑多轮不断累积。改成持有引用并在 `finally` 关闭，同时把"客户端回调执行器"和"压测并发载体"拆成两个，避免职责混用。
7. **配置开关不生效比没有更坑**：`BenchOptions` 里定义了 `abortOnReject`，但 `ExecutorFactory` 从头到尾没读过它，饱和策略永远是 AbortPolicy。留着只会让人以为能切换策略——删掉，把"为什么不用 CallerRunsPolicy"写进注释。

## 结论

| 场景 | 结论 | 量化 |
|---|---|---|
| IO 密集（并行编排） | 虚拟线程吞吐随并发线性上涨，平台池被线程数锁死 | **5.0～9.9 倍** |
| 饱和（请求打穿线程） | 平台池拒绝请求，虚拟线程零拒绝 | 9,400 → 0 |
| pinning（锁内阻塞） | `synchronized` 让虚拟线程退化成平台线程 | 吞吐差 **67 倍** |
| CPU 密集 | 无收益，瓶颈在核数不在线程模型 | 1.01 倍（噪声） |
| HTTP 服务（Tomcat） | 只换 executor 即可受益，池越小收益越大（抖动 ±10~20%） | **1.05～5.4 倍（区间）** |

一句话：**虚拟线程买的是"等待"，不是"算力"**。IO 等待占比越高、并发越大，收益越大；CPU 密集别换；需要限流背压的场景别换；换的同时必须排查 `synchronized` 临界区内的阻塞调用。

## 后续可做的

- **真实链路复测**：当前用的是可控阻塞（`sleep` 模拟等待），趋势可信但绝对值不能直接搬到线上。下一步把模拟 IO 换成真实 DB / HTTP / MQ 调用，量化端到端收益。
- **pinning 全量排查**：除 `synchronized` 外，`Object.wait()`、native 方法也会 pin。真实项目要沿调用链排查连接池、驱动、序列化库内部的实现。
- **与背压 / 限流组合**：虚拟线程近乎无限，压根不限流。高并发入口需要配 `Semaphore` 或有界队列做准入，避免把压力无损传导给下游。
- **`ScopedValue` 迁移**：JDK 24 起可用 `ScopedValue` 替代 `ThreadLocal` 做上下文传递，配合结构化并发，比手动 set/reset 更安全。
